GITMETRICS INTERVIEW GUIDE
===========================

Source of truth: the current repository contents. This guide describes what the code actually implements. Any proposal that is not present in the code is labeled RECOMMENDED IMPROVEMENT. Missing behavior is labeled CURRENTLY NOT IMPLEMENTED or NOT EVIDENT FROM THE CODE.

1. PROJECT OVERVIEW
===================

GitMetrics is a Spring Boot REST backend that retrieves public GitHub repository metrics, calculates a simple repository health score, stores timestamped snapshots, and reports a growth trend. Users can register, log in, add repositories to a watchlist, and view a dashboard of watched repositories.

The problem it addresses is repeated manual checking of GitHub repository statistics. Instead of opening GitHub and comparing stars, forks, and open issues by hand, a user can submit a repository URL. GitMetrics fetches current values, persists a snapshot, and compares recent health scores. A scheduled job also refreshes all known repositories hourly.

Typical users would be developers, students, team leads, or project owners who want a lightweight history and dashboard for repositories. The code does not implement a frontend, so the client is currently a REST client, browser-based API tool, or future frontend. A visual frontend is CURRENTLY NOT IMPLEMENTED.

Main implemented features:
- User registration with BCrypt password hashing.
- Login with email and password.
- Stateless JWT authentication for protected endpoints.
- GitHub repository tracking by URL.
- GitHub REST API lookup of repository name, owner, stars, forks, and open issues.
- Persistence of repositories and metric snapshots.
- Health score calculation.
- Growth trend based on the two newest snapshots.
- User watchlists and dashboard responses.
- Hourly synchronization of every stored repository.
- Basic translation of GitHub 404 and 403 errors into API responses.

Why it is useful compared with manually using GitHub:
- It retains historical snapshots rather than showing only the current GitHub page.
- It calculates a repeatable health score.
- It gives each user a watchlist and dashboard-oriented response.
- It refreshes tracked repositories automatically once per hour.
- It creates a backend boundary where caching, alerts, richer analytics, or a frontend could later be added.

30-SECOND INTERVIEW EXPLANATION
-------------------------------
GitMetrics is a Spring Boot REST API for monitoring GitHub repositories. An authenticated user can register, log in, track a repository URL, add it to a watchlist, and retrieve dashboard data. The backend calls the GitHub REST API through Spring RestClient, maps the response into a DTO, calculates a health score from stars, forks, and open issues, and stores timestamped snapshots in PostgreSQL through JPA. A scheduled service refreshes repositories hourly, and JWTs protect all endpoints except registration and login.

1-MINUTE EXPLANATION
---------------------
I built GitMetrics as a layered Spring Boot application. Controllers expose repository and user endpoints, services contain the application logic, Spring Data repositories access PostgreSQL, and JPA entities model users, repositories, snapshots, and the many-to-many watchlist relationship. GitHubService calls api.github.com, stores a repository if necessary, saves a snapshot, and calculates health and trend data through AnalysisService. Authentication uses BCrypt for passwords and signed JWTs in a stateless Spring Security filter chain. The application is packaged with Maven and can run in a two-stage Java 21 Docker image. The current implementation is a backend API rather than a complete web application.

2-3 MINUTE EXPLANATION
-----------------------
The application starts at GitMetricsApplication, where Spring Boot auto-configuration and scheduling are enabled. Incoming HTTP requests are handled by GitHubController or UserController. SecurityConfig permits only registration and login without authentication; all other requests are stateless and pass through JwtFilter. During login, AuthenticationManager uses MyUserDetailsService and UserRepo to load the user, DaoAuthenticationProvider checks the BCrypt password, and JWTService creates a token containing the email as the subject. On later calls, JwtFilter extracts a Bearer token, validates its signature and expiry, loads the user, and puts a UsernamePasswordAuthenticationToken into Spring Security's SecurityContext.

For repository operations, GitHubService normalizes the submitted URL enough to extract owner and repository path, calls GitHub's GET /repos/{owner}/{repo} endpoint, deserializes the result into GitHubResponse, and either finds an existing github entity by URL or persists a new one. It calculates (stars + 2 * forks) / (open issues + 1), stores a snap entity with capturedAt, and uses the two newest snapshots to produce a growth string. UserService reuses this workflow when adding a repository to a watchlist and builds dashboard responses from the user's repositories and their latest snapshots. SyncService performs the same tracking workflow once every hour for every stored repository.

This design is a conventional layered monolith. It is simple to deploy and understand, and PostgreSQL is appropriate for relationships and historical records. The main limitations are limited validation and exception handling, synchronous external calls, no GitHub authentication token, no frontend, only a context-load test, and a fallback JWT secret in configuration that should not be used in production.

4. REQUEST LIFECYCLE / END-TO-END FLOW
=======================================

PRIMARY FLOW: POST /github/track?url=https://github.com/spring-projects/spring-boot

  Client
    |
    | POST /github/track?url=...
    v
  SecurityConfig / JwtFilter
    |
    | JWT required because only register/login are public
    v
  GitHubController.trackRepo(String url)
    |
    v
  GitHubService.githubresponse(String url)
    |
    | extractPath(url) -> owner/repository
    v
  RestClient GET /repos/{owner}/{repo}
    |
    v
  GitHubResponse record
    |
    +--> GitRepo.findByUrl(url)
    |       +--> existing github entity
    |       +--> or save a new github entity
    |
    +--> AnalysisService.calculateHealthScore(stars, forks, issues)
    |
    +--> build snap with capturedAt and repository relation
    |
    +--> SnapRepo.save(snapshot)
    |
    +--> load newest two snapshots and calculate trend
    v
  GitHubResponse serialized as JSON
    |
    v
  HTTP 200 response

Important accuracy: the track method returns GitHubResponse, not RepoAnalysisResponse. The calculated trend is printed to standard output in GitHubService but is not included in the track response.

FLOW 2: LOGIN
POST /github/users/login with a User JSON body.
1. UserController.login receives the body.
2. UserService.verify creates UsernamePasswordAuthenticationToken with email and submitted password.
3. AuthenticationManager delegates to DaoAuthenticationProvider.
4. MyUserDetailsService loads the user with UserRepo.findByEmail.
5. BCrypt compares the submitted password with the stored hash.
6. If authenticated, JWTService.generateToken uses the email as subject and creates a token that expires after ten hours.
7. The controller returns {"token":"<JWT>"}.

FLOW 3: ADD TO WATCHLIST
POST /github/users/watchlist?url=... with Authorization: Bearer <JWT>.
1. JwtFilter validates the token and sets the SecurityContext.
2. UserController obtains authentication.getName(), which is the email from the JWT subject.
3. UserService.addRepoToWatchlist loads the User.
4. It calls GitHubService.githubresponse, which fetches current data and creates a repository/snapshot if needed.
5. It looks up the repository with GitRepo.findByUrl.
6. It adds the repository to User.watchlists and saves the user.
7. The many-to-many relationship is written through user_watchlists.
8. The controller returns a success message.

FLOW 4: DASHBOARD
GET /github/users/dashboard with a valid JWT.
1. JwtFilter authenticates the request.
2. UserController gets the authenticated email.
3. UserService.getUserDashboard loads the user and lazily accesses watchlists inside a read-only transaction.
4. For every watched github entity, SnapRepo loads up to two newest snapshots.
5. The newest values become stars, forks, issues, and healthScore; empty history produces zeros.
6. AnalysisService creates a trend string.
7. UserService returns a list of RepoAnalysisResponse records.

FLOW 5: HOURLY SYNC
1. @EnableScheduling activates scheduled jobs.
2. SyncService.syncData runs at cron 0 0 * * * *, at the start of every hour.
3. GitRepo.findAll loads all repositories.
4. For each repository, GitHubService.githubresponse fetches current GitHub data and saves a new snapshot.
5. Each repository is isolated by a try/catch, so one failure does not stop the loop.
6. Status is written with System.out.println.

5. HOW USERS GIVE INPUT
========================

General rules:
- Query parameters are used for repository URLs: url.
- JSON request bodies are used for User registration and login.
- Protected requests need Authorization: Bearer <JWT>.
- There are no path variables in the controllers.
- There are no documented optional parameters. url is required by the Java method signature and Spring request binding.
- JSON validation annotations such as @Valid, @NotBlank, and @Email are absent.

REGISTER
METHOD: POST
ENDPOINT: /github/users/register
INPUT: JSON User body with email, password, and optionally name. id and watchlists should not be supplied by a normal client.
HEADERS: Content-Type: application/json. No JWT required.
REQUEST BODY:
{"email":"alex@example.com","password":"example-password","name":"Alex"}
EXAMPLE REQUEST:
curl -X POST http://localhost:8080/github/users/register -H "Content-Type: application/json" -d "{\"email\":\"alex@example.com\",\"password\":\"example-password\",\"name\":\"Alex\"}"
WHAT HAPPENS: UserController calls UserService.register. The service checks existsByEmail, hashes the password with BCrypt strength 12, and saves the entity.
EXAMPLE RESPONSE: A serialized User entity containing id, email, name, and watchlists. The current controller returns the entity directly.
POSSIBLE ERRORS: Duplicate email throws a generic RuntimeException; no dedicated handler maps it. Missing or malformed fields are not Bean Validation errors because validation is absent. Returning the entity can expose the stored password hash.

LOGIN
METHOD: POST
ENDPOINT: /github/users/login
INPUT: JSON User body; email and password are used.
HEADERS: Content-Type: application/json. No JWT required.
REQUEST BODY:
{"email":"alex@example.com","password":"example-password"}
EXAMPLE REQUEST:
curl -X POST http://localhost:8080/github/users/login -H "Content-Type: application/json" -d "{\"email\":\"alex@example.com\",\"password\":\"example-password\"}"
WHAT HAPPENS: AuthenticationManager verifies credentials through UserRepo and BCrypt. JWTService creates a ten-hour signed token.
EXAMPLE RESPONSE: {"token":"<JWT>"}
POSSIBLE ERRORS: Invalid credentials are intended to produce HTTP 401 from the controller, although the authentication provider may throw before the string "Fail" branch is reached. Invalid JWT parsing is not handled by GlobalExceptionHandler.

TRACK REPOSITORY
METHOD: POST
ENDPOINT: /github/track?url=https://github.com/owner/repository
INPUT: Required query parameter url. The implementation expects a GitHub-style URL containing owner and repository segments.
HEADERS: Authorization: Bearer <JWT>; no GitHub token header is added by GitMetrics.
REQUEST BODY: None.
WHAT HAPPENS: GitHubController.trackRepo calls GitHubService.githubresponse. The service calls GitHub, persists repository and snapshot data, and returns GitHubResponse.
EXAMPLE RESPONSE:
{"name":"spring-boot","stars":...,"forks":...,"issues":...,"owner":{"login":"spring-projects"}}
POSSIBLE ERRORS: GitHub 404 and 403 are handled by GlobalExceptionHandler. Empty, malformed, or non-GitHub URLs can cause array-index or other runtime failures. A duplicate URL is found by the unique URL lookup. No retry or timeout policy is visible.

ANALYZE REPOSITORY
METHOD: GET
ENDPOINT: /github/analysis?url=https://github.com/owner/repository
INPUT: Required query parameter url.
HEADERS: Authorization: Bearer <JWT>.
REQUEST BODY: None.
WHAT HAPPENS: GitHubController calls GitHubService.getRepoAnalysis. It fetches current GitHub data, requires a pre-existing local repository with GitRepo.findByUrl(url), loads two snapshots, calculates current health and trend, and returns RepoAnalysisResponse.
EXAMPLE RESPONSE:
{"name":"spring-boot","owner":"spring-projects","stars":100,"forks":50,"issues":10,"healthScore":18.18,"growthTrend":"Growth: 4.25% compared to previous check."}
POSSIBLE ERRORS: If the repository was never tracked, or the exact URL differs from the stored URL, orElseThrow produces an unhandled exception. GitHub 404/403 are translated by the global handler.

ADD WATCHLIST
METHOD: POST
ENDPOINT: /github/users/watchlist?url=https://github.com/owner/repository
INPUT: Required url query parameter.
HEADERS: Authorization: Bearer <JWT>.
REQUEST BODY: None.
WHAT HAPPENS: The authenticated email identifies the user. UserService fetches the repository through GitHubService, obtains the local entity, adds it to the Set, and saves the user.
EXAMPLE RESPONSE: {"message":"Repository added to watchlist successfully."}
POSSIBLE ERRORS: Missing/invalid JWT, invalid repository URL, GitHub failure, missing local user, or persistence failure. There is no explicit duplicate-watchlist response; Set semantics normally avoid duplicate links.

DASHBOARD
METHOD: GET
ENDPOINT: /github/users/dashboard
INPUT: No body or query parameters.
HEADERS: Authorization: Bearer <JWT>.
REQUEST BODY: None.
WHAT HAPPENS: UserService loads the authenticated user's watchlist and up to two snapshots per repository, then returns a list of RepoAnalysisResponse.
EXAMPLE RESPONSE:
[{"name":"spring-boot","owner":"spring-projects","stars":100,"forks":50,"issues":10,"healthScore":18.18,"growthTrend":"Not enough data to calculate growth yet."}]
POSSIBLE ERRORS: Unauthenticated request, unknown user, lazy-loading/persistence failure, or database failure. An empty watchlist returns an empty JSON array.

7. AUTHENTICATION AND AUTHORIZATION
====================================

Simple explanation:
GitMetrics has its own account system. A user registers with email and password. The password is hashed before storage. On login, the backend returns a signed JWT. The client sends that token on protected requests. The backend validates it and uses the email inside it to identify the user.

Technical trace:
1. SecurityConfig permits /github/users/register and /github/users/login.
2. It requires authentication for every other request.
3. It disables CSRF and sets SessionCreationPolicy.STATELESS.
4. JwtFilter runs before UsernamePasswordAuthenticationFilter.
5. JwtFilter reads Authorization and requires the Bearer prefix.
6. JWTService extracts the subject and verifies the HMAC signature using the configured Base64 secret.
7. MyUserDetailsService loads User by email through UserRepo.
8. validateToken checks subject equality and expiration.
9. A UsernamePasswordAuthenticationToken is placed in SecurityContextHolder.
10. Controller Authentication.getName() returns the email.

Authentication answers:
- JWTs: Yes.
- Sessions: Server-side sessions are disabled; the application is stateless.
- OAuth: CURRENTLY NOT IMPLEMENTED.
- GitHub token: CURRENTLY NOT IMPLEMENTED. GitMetrics accesses GitHub with only Accept and User-Agent headers.
- API key: No application API-key mechanism is evident.
- Token storage: The backend returns the JWT. Client-side storage is NOT EVIDENT FROM THE CODE.
- Token passed to GitHub: It is not. The GitMetrics JWT authenticates the caller to GitMetrics, not to GitHub.
- Authorization: Every non-public endpoint requires authenticated access, but no endpoint-specific roles or ownership checks are implemented. UserPrincipal always grants "USER".

Authentication means proving identity. Authorization means deciding what an authenticated identity may do. This code implements basic authorization at the endpoint level, but not role-based authorization or fine-grained resource policies.

Security observations:
- The JWT secret is configurable through JWT_SECRET, but application.properties also contains a fallback literal secret. Do not reproduce it or use it in production.
- The database password appears in commented configuration. It is still sensitive source material and should be removed and rotated if it was ever real.
- RECOMMENDED IMPROVEMENT: Require JWT_SECRET with no source-controlled fallback.
- RECOMMENDED IMPROVEMENT: Use an external secret manager and rotate keys.
- RECOMMENDED IMPROVEMENT: Return a safe registration DTO rather than User, so the password hash cannot be serialized.
- RECOMMENDED IMPROVEMENT: Add explicit exception handling for malformed, expired, and invalid JWTs.
- RECOMMENDED IMPROVEMENT: Add refresh-token or short-lived-token policy if long sessions are required.
- RECOMMENDED IMPROVEMENT: Add roles/authorities only if actual authorization requirements need them.

8. GITHUB API INTEGRATION
==========================

Configuration:
- Base URL: https://api.github.com in AppConfig.
- Default headers: Accept: application/json and User-Agent: GitMetrics-App.
- Client: one Spring RestClient bean.

Calls:
- HTTP GET /repos/{owner}/{repo} in GitHubService.githubresponse.
- HTTP GET /repos/{owner}/{repo} in GitHubService.getRepoAnalysis.
- Owner and repository are extracted from the submitted URL by extractPath.

Parsing:
GitHubResponse is a Java record. Jackson maps GitHub's stargazers_count, forks_count, and open_issues_count into stars, forks, and issues through @JsonProperty. The nested Owner record maps the login.

There is no:
- GitHub OAuth flow.
- GitHub Authorization header.
- Pagination, because the only endpoint returns one repository resource.
- Retry, backoff, circuit breaker, cache, timeout, or bulkhead configuration evident in the code.
- Explicit handling of GitHub API 500 or network errors.

GitMetrics backend versus GitHub API:
- GitHub owns current public repository metadata.
- GitMetrics owns user accounts, watchlists, health calculation, snapshots, and dashboard responses.
- GitMetrics calls GitHub synchronously during tracking, analysis, watchlist addition, and scheduled synchronization.

REST client choice is reasonable for a small synchronous integration because it keeps the call readable and the base URL/header setup centralized. RECOMMENDED IMPROVEMENT: configure timeouts and resilience policies.

11. DESIGN PATTERNS AND ARCHITECTURAL PRINCIPLES
=================================================

Layered architecture
- Used by controller, service, repo, model, and configuration packages.
- Separates HTTP handling, application logic, persistence, and configuration.
- Useful for explaining request flow and keeping controllers thin.

MVC-style web architecture
- Controllers handle requests and responses, services act as application logic, and model classes represent data.
- This is a REST adaptation of the MVC separation.

Dependency injection / Inversion of Control
- Spring injects UserService, GitHubService, repositories, RestClient, and security components with @Autowired.
- Beans are created by Spring and wired by type.
- It avoids manually constructing dependencies and improves testability, although constructor injection would be clearer.

Repository pattern
- GitRepo, UserRepo, and SnapRepo abstract persistence behind interfaces extending JpaRepository.
- Derived query names express database queries without handwritten SQL.

DTO pattern
- GitHubResponse prevents the external GitHub response shape from being used as a JPA entity.
- RepoAnalysisResponse exposes the application result shape.
- The registration endpoint currently bypasses a safe output DTO by returning User directly.

Builder pattern
- snap.builder() constructs a snapshot with multiple fields clearly in GitHubService.
- Lombok generates the builder.

Singleton-like Spring beans
- AppConfig's RestClient and annotated services are managed beans, normally one instance per application context by default.
- This is a Spring bean scope rather than a manually implemented singleton.

Strategy pattern
CURRENTLY NOT EVIDENT as a deliberate pattern. AnalysisService contains fixed formulas; there is no interchangeable strategy interface.

Factory pattern
CURRENTLY NOT EVIDENT as an application pattern. Spring internally creates beans, but the project does not implement a factory abstraction.

12. SPRING BOOT EXPLANATION
============================

@SpringBootApplication on GitMetricsApplication combines configuration, component scanning, and auto-configuration. Spring discovers @RestController, @Service, @Repository, @Component, and @Configuration classes under the root package.

@RestController marks GitHubController and UserController as HTTP controllers whose return values are serialized to JSON.

@RequestMapping establishes controller prefixes. @PostMapping and @GetMapping connect HTTP methods and paths to Java methods.

@Service marks application classes such as GitHubService and UserService as injectable business-layer beans.

@Repository marks Spring Data repository interfaces. Spring creates implementations at runtime.

@Component marks JwtFilter for component scanning.

@Configuration marks AppConfig and SecurityConfig as bean configuration classes.

@Bean explicitly creates RestClient, SecurityFilterChain, AuthenticationProvider, and AuthenticationManager objects.

@Autowired requests dependency injection by field. RECOMMENDED IMPROVEMENT: use constructor injection, which makes dependencies explicit and fields final.

application.properties supplies values such as spring.application.name, JPA behavior, server.port, and jwt.secret. `${PORT:8080}` means use PORT if present, otherwise 8080. `${JWT_SECRET:...}` means use JWT_SECRET if present, otherwise the source-controlled fallback; this fallback is a security weakness.

Spring Boot runs an embedded servlet server, so the packaged JAR can start with java -jar. Docker starts that JAR on the configured port.

13. ERROR HANDLING
===================

Implemented global handling:
- HttpClientErrorException.NotFound -> HTTP 404 with {"error":"Repository not found on GitHub."}.
- HttpClientErrorException.Forbidden -> HTTP 403 with {"error":"GitHub API rate limit exceeded."}.

Controller-level login response:
- UserController intends to return HTTP 401 with an error map when verification returns "Fail".
- AuthenticationManager commonly throws an authentication exception for bad credentials, and GlobalExceptionHandler does not handle it. Exact runtime response depends on Spring Security behavior; a dedicated authentication handler is RECOMMENDED.

Unhandled or weakly handled cases:
- Duplicate registration throws RuntimeException("Email already in use") with no custom mapping.
- Missing user throws RuntimeException("User not found").
- Missing tracked repository in analysis uses orElseThrow with no specific exception.
- Malformed repository URL can cause runtime failures from parts[0]/parts[1].
- Invalid JWT parsing/expiry exceptions are not mapped by GlobalExceptionHandler.
- Database failures are not mapped.
- Network errors and GitHub 5xx responses are not explicitly handled.
- No validation error response exists because Bean Validation is not configured or used.

RECOMMENDED IMPROVEMENT: create domain exceptions and a complete @RestControllerAdvice that returns consistent error bodies, correlation IDs, and safe messages for 400, 401, 403, 404, 409, 429, and 500 cases.

19. PERFORMANCE AND SCALABILITY
===============================

Current behavior:
- GitHub calls are synchronous and block the request thread.
- Every tracking, analysis, watchlist addition, and hourly sync can call GitHub.
- Snapshots are appended; there is no retention policy.
- Dashboard loads the watchlist, then queries snapshots per repository, which can become an N+1 query pattern.
- Only two snapshots are requested for each repository.
- No application cache is configured.
- Spring Boot/JPA provides a database connection pool through its defaults, but no explicit pool tuning is present.
- No pagination exists for watchlists, dashboards, or all repository synchronization.
- No asynchronous queue is used.

One user:
- The synchronous flow is simple and likely adequate for small requests.
- GitHub response latency directly affects the API response.

One thousand users:
- Concurrent requests can consume web threads while waiting for GitHub.
- Repeated identical lookups can hit GitHub rate limits.
- Dashboard query count grows with watchlist size.
- Snapshot table grows indefinitely.
- Multiple application replicas would duplicate hourly sync work.

RECOMMENDED IMPROVEMENTS:
- Cache current repository data with a short TTL.
- Add GitHub conditional requests/ETags where supported.
- Configure HTTP timeouts, retry with backoff for transient failures, and circuit breaking.
- Queue scheduled synchronization and limit concurrency.
- Coordinate scheduled jobs with a distributed lock when horizontally scaled.
- Batch dashboard snapshot queries or use a projection query.
- Add repository and capturedAt indexes and retention/archival policy.
- Add pagination to dashboard/watchlist operations.
- Use authenticated GitHub access where appropriate, respecting GitHub terms and rate limits.
- Add metrics for latency, failure rate, API quota, and database timings.

There is no vector-search performance consideration because vectors are CURRENTLY NOT IMPLEMENTED.

22. IMPORTANT TECHNICAL DECISIONS
==================================

Decision: REST API.
Why: Controllers expose focused HTTP endpoints and JSON DTOs for client independence.
Alternative: GraphQL or server-rendered MVC.
Trade-off: REST is simple, but clients may require multiple calls and the response shapes are fixed.

Decision: PostgreSQL/JPA.
Why: Users, repositories, snapshots, and watchlist links are relational.
Alternative: document database.
Trade-off: relational constraints and joins are strong, but schema changes require migration discipline.

Decision: GitHub REST API.
Why: The required repository metrics are available from a single public endpoint.
Alternative: GitHub GraphQL.
Trade-off: REST is simpler here; GraphQL could select fields more flexibly but adds complexity.

Decision: DTO records.
Why: External API shape and analysis response are separate from database entities.
Trade-off: Some mapping code is needed; direct entity exposure is avoided for those responses, although registration still exposes User directly.

Decision: Layered monolith.
Why: The project is small and the workflows share persistence and GitHub integration.
Alternative: microservices.
Trade-off: simple deployment and debugging versus less independent scaling.

Decision: Synchronous GitHub calls.
Why: The caller receives an immediate tracking/analysis result.
Trade-off: request latency and API availability directly affect the user request.

Decision: Hourly in-process scheduler.
Why: It provides automatic refresh without a separate worker system.
Trade-off: not coordinated across replicas and may create many API calls.

Decision: Docker multi-stage build.
Why: Separates Maven build dependencies from runtime application packaging.
Trade-off: image builds are repeatable, but tests are skipped in the Docker build.

pgvector decision: None. pgvector is not included or used.

23. TRADE-OFFS
==============

REST versus GraphQL: GitMetrics currently uses REST because one repository resource and a few application operations are sufficient. GraphQL might reduce over-fetching for a richer dashboard but would add schema and resolver complexity.

PostgreSQL versus NoSQL: PostgreSQL matches many-to-many watchlists and one-to-many snapshots. NoSQL could scale flexible documents but would make relational integrity and query relationships less natural.

Synchronous versus asynchronous GitHub calls: synchronous behavior is easy to understand and gives an immediate result; asynchronous jobs would improve resilience and throughput but require job state and client polling or notifications.

Caching versus always fetching fresh data: current analysis fetches current GitHub data, which reduces staleness but increases latency and rate-limit usage. A short cache would improve performance with controlled staleness.

Monolith versus microservices: current monolith minimizes operational overhead. At large scale, GitHub ingestion and dashboard querying could be separated, but service boundaries and distributed consistency would cost complexity.

Local/in-process scheduler versus external scheduler: current scheduling is simple; an external scheduler or distributed lock is safer with multiple replicas.

JWT versus server sessions: JWTs fit stateless API deployment, but revocation is harder. Sessions simplify revocation but require shared session state when scaled.

24. WHAT HAPPENS IF...
=======================

GitHub is down: RestClient throws a network/client exception. No retry or friendly general GitHub-unavailable handler is implemented. The request likely fails with a framework error; scheduled sync catches the exception per repository and continues. RECOMMENDED IMPROVEMENT: timeout, retry, circuit breaker, and 503 response.

Repository does not exist: GitHub returns 404, RestClient raises HttpClientErrorException.NotFound, and GlobalExceptionHandler returns 404 with an error message.

User gives an invalid username: There is no username input in the API. Users submit a repository URL; GitHub owner is parsed from the URL. Invalid URL structure can cause runtime errors rather than a controlled 400.

GitHub rate-limits the application: A GitHub 403 is mapped to HTTP 403 with a rate-limit message. No quota inspection, wait, retry, or backoff is implemented.

PostgreSQL is unavailable: Startup or repository operations fail through the datasource/JPA layer. No custom database error response is implemented.

Database contains no data: Dashboard for an authenticated user with no watchlist returns an empty list. Sync finds no repositories and does nothing. Analysis for an untracked URL throws from orElseThrow.

Two users request the same repository: Each call checks by URL and may race before one sees the other's insert. The unique URL constraint protects database uniqueness, but duplicate-insert exception handling is not implemented. Both users can link the same repository through the many-to-many table.

GitHub returns 500: No explicit handler exists for server errors, so the framework's default error behavior applies. Scheduled sync catches the exception and continues.

Authentication fails: Missing authentication on a protected endpoint is rejected by Spring Security. Invalid credentials are intended to produce 401, but authentication exceptions are not explicitly handled in the global advice. Invalid JWT parse exceptions are also not explicitly mapped.

Request contains invalid data: Bean Validation is absent. Missing request parameters may be rejected by Spring; malformed bodies or malformed URLs can result in framework/runtime errors rather than a standardized validation response.

Application restarts: JWTs remain valid until expiry if the same secret is used, because sessions are stateless. Stored users, repositories, watchlists, and snapshots remain in PostgreSQL. Scheduled synchronization resumes when the application starts and reaches the next cron time.

One thousand requests arrive simultaneously: Web threads may block on synchronous GitHub calls and database operations. There is no visible rate limiter, queue, cache, or circuit breaker. The application and GitHub may become bottlenecks.

30. 2-MINUTE PROJECT PITCH
===========================

GitMetrics is a layered Spring Boot REST application for tracking GitHub repository health over time. The main problem is that GitHub shows current repository counts, but it does not give this application a user-specific watchlist and custom historical comparison workflow. GitMetrics lets a user register, log in, track a repository URL, add it to a watchlist, and retrieve dashboard results.

The request enters through a controller. Spring Security protects everything except registration and login. Passwords are hashed with BCrypt, and login produces a signed ten-hour JWT. On protected requests, JwtFilter validates the bearer token, loads the user by email, and puts the authenticated identity in the SecurityContext.

GitHubService is the main integration service. It extracts an owner and repository from the submitted URL and calls GitHub's GET /repos/{owner}/{repo} endpoint through a configured RestClient. The JSON is mapped into GitHubResponse. The service finds or creates a github entity, calculates the formula (stars + 2 * forks) / (issues + 1), and saves a snap entity with the metric values and capture time. It then reads the two newest snapshots and AnalysisService creates a growth string. UserService uses the same ingestion flow when a user adds a repository to a watchlist, and it builds dashboard RepoAnalysisResponse objects from the latest snapshots.

The persistence layer uses Spring Data JPA repositories for users, repositories, and snapshots. A User has a many-to-many watchlist relationship with github, and github has a one-to-many relationship with snap. SyncService runs this tracking workflow at the start of every hour. The app is built with Maven and packaged in a multi-stage Java 21 Docker image.

The most important limitations are that validation and tests are minimal, error handling covers only two GitHub statuses, GitHub calls are synchronous, no GitHub token or caching exists, the scheduled job is not coordinated across replicas, and a fallback JWT secret is present in configuration. Those are the first production improvements I would discuss.

31. PROJECT WEAKNESSES
======================

1. Fallback JWT secret in source configuration.
Why it matters: Anyone with the source can potentially forge tokens when the environment variable is absent.
Improvement: Require an external secret, rotate any exposed key, and fail startup if missing.

2. Commented database credentials.
Why it matters: Comments remain in repository history and may reveal real credentials.
Improvement: Remove them and rotate if real.

3. User entity returned on registration.
Why it matters: It can serialize the BCrypt hash.
Improvement: Return a safe response DTO and never expose password fields.

4. No Bean Validation.
Why it matters: Bad email, empty passwords, and malformed URLs reach business logic.
Improvement: Add validated request DTOs and consistent 400 responses.

5. Fragile URL parsing.
Why it matters: String replacement and array indexing do not robustly validate URLs.
Improvement: Parse URI, enforce github.com host, canonicalize owner/repo, and reject extra/invalid paths.

6. Incomplete exception handling.
Why it matters: Database, network, JWT, duplicate-key, and GitHub 5xx errors can become generic failures.
Improvement: Add domain exceptions and a complete global handler.

7. No resilience policy.
Why it matters: A slow/down GitHub can block requests.
Improvement: Timeouts, retry/backoff, circuit breaker, caching, and asynchronous refresh.

8. Potential N+1 dashboard queries.
Why it matters: One snapshot query is made per watched repository.
Improvement: Batch projection query or precomputed latest snapshot table.

9. Unbounded snapshots.
Why it matters: Hourly sync grows data forever.
Improvement: retention, archival, aggregation, or configurable history policy.

10. In-process scheduled job.
Why it matters: Multiple replicas duplicate work.
Improvement: distributed lock or external worker queue.

11. Minimal tests.
Why it matters: Core business, security, integration, and error paths can regress unnoticed.
Improvement: unit, MockMvc, repository, Testcontainers, and security tests.

12. Field injection.
Why it matters: Dependencies are implicit and harder to test.
Improvement: constructor injection.

13. Direct System.out logging and SQL logging.
Why it matters: Poor production observability and possible sensitive log exposure.
Improvement: structured logger, redaction, metrics, tracing, and production-safe SQL settings.

14. No API documentation.
Why it matters: Clients must infer contracts from source.
Improvement: OpenAPI/Swagger documentation and versioned request/response schemas.

15. No explicit cloud deployment.
Why it matters: Docker alone does not provide database, secrets, networking, or scaling.
Improvement: deployment manifests, managed PostgreSQL, secret manager, HTTPS, health checks, and CI/CD.
